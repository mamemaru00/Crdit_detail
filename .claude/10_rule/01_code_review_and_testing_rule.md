# コードレビュー・テストルール

## 概要
Issue #78（/gpt/confirm 500エラー）で発見された3つのバグの根本原因分析に基づき、
同種のバグの再発を防止するための開発ルールを定める。

## 背景（Issue #78 で発見されたバグ）

| Bug | 内容 | 根本原因パターン |
|-----|------|-----------------|
| Bug 1 | 未定義変数 `confirmed_data` の参照 | 変数リネーム時の参照漏れ |
| Bug 2 | `batch_update_cells` の引数不一致（3引数 vs 実際は2引数） | 関数シグネチャの未確認 |
| Bug 3 | `os.getenv('SPREADSHEET_ID')` でセッション値の代わりに環境変数を参照 | データフローの理解不足 |

## ルール 1: 静的解析の必須実行

### 目的
未定義変数参照、未使用変数、関数シグネチャ不一致をランタイム前に検出する。

### ルール
- コード変更後、コミット前に以下の静的解析を実行すること
- `py_compile` のみでは不十分。以下のツールを併用する

### 必須チェック項目

| ツール | 検出対象 | コマンド例 |
|--------|----------|-----------|
| flake8 | 未定義変数(F821)、未使用import(F401)、構文エラー | `flake8 app.py --select=E,F,W` |
| pyright または mypy | 型不一致、関数シグネチャ不一致 | `pyright app.py` |

### 段階的導入
1. **即時**: flake8 による基本チェック（F821: undefined name が最優先）
2. **次期**: pyright/mypy による型チェック（型ヒント整備と並行）
3. **将来**: pre-commit hook への組み込み

## ルール 2: 変数リネーム時の全参照チェック

### 目的
変数名・関数名の変更時に、全ての参照箇所を漏れなく更新する。

### ルール
- 変数名・関数名を変更する場合、以下の手順を必ず実行すること

### 手順
1. **変更前**: 対象の変数名・関数名で全文検索（grep）を実行し、参照箇所を列挙する
2. **変更実施**: 全ての参照箇所を更新する
3. **変更後**: 再度全文検索を実行し、旧名称が残っていないことを確認する
4. **検証**: flake8 で未定義変数エラーが出ないことを確認する

### 例（Issue #78 Bug 1 の場合）
```bash
# 変更前: confirmed_data の参照箇所を確認
grep -rn "confirmed_data" app.py

# 変更後: 旧名称が残っていないことを確認
grep -rn "confirmed_data" app.py
# → 0件であることを確認
```

## ルール 3: 関数呼び出し時のシグネチャ確認

### 目的
モジュール間の関数呼び出しで、引数の数・型・順序の不一致を防止する。

### ルール
- 他モジュールの関数を呼び出すコードを新規作成・変更する場合、
  呼び出し先の関数定義を必ず確認すること

### 確認項目
1. **引数の数**: 呼び出し元と呼び出し先で引数の数が一致しているか
2. **引数の型**: 渡している値の型が、関数定義の型ヒントと一致しているか
3. **引数の順序**: 引数の順序が正しいか（特に同じ型の引数が複数ある場合）
4. **戻り値の型**: 戻り値の使い方が、関数定義の戻り値型と一致しているか

### 禁止事項
- 関数定義を確認せずに「想像上のインターフェース」でコードを書くことを禁止する
- 特に、リファクタリングで呼び出し方法を変更する場合は、
  呼び出し先のソースコードを必ず参照すること

## ルール 4: データフロー整合性の検証

### 目的
複数エンドポイントにまたがるデータの受け渡しの不整合を防止する。

### ルール
- 複数エンドポイント間でセッションデータを介してデータを受け渡す場合、
  以下の検証を行うこと

### 検証項目
1. **書き込み箇所の特定**: データがセッションに書き込まれる箇所を特定する
2. **読み取り箇所の特定**: データがセッションから読み取られる箇所を特定する
3. **キー名の一致**: 書き込みキーと読み取りキーが一致しているか確認する
4. **データソースの一貫性**: 同じデータを環境変数とセッションの両方から取得していないか確認する
5. **未取得時のエラーハンドリング**: セッションデータが存在しない場合の処理が適切か確認する

### 禁止事項
- ユーザー入力値をセッションに保存している場合、同じ値を環境変数から取得することを禁止する
  （環境変数はフォールバック値ではなく、設定値として使用する）

### 例（Issue #78 Bug 3 の場合）
```
[悪い例] spreadsheet_id = os.getenv('SPREADSHEET_ID')  # ユーザー入力値と異なる可能性
[良い例] spreadsheet_id = session_data.get('spreadsheet_id')  # セッションから一貫して取得
```

## ルール 5: エンドポイント実装時のテスト要件

### 目的
エンドポイントの実装・変更時に、最低限のテストを義務化する。

### ルール
- 新規エンドポイント実装時、または既存エンドポイントの大幅な変更時は、
  以下のテストを実施すること

### 必須テスト

| テスト種別 | 内容 | 例 |
|-----------|------|-----|
| 正常系テスト | 正しい入力で期待通りの出力が返ることを確認 | POST /gpt/confirm に正しいJSONを送信し、200が返ること |
| 異常系テスト | 不正な入力でエラーレスポンスが返ることを確認 | 空のclassificationsを送信し、400が返ること |
| フロー通しテスト | 前後のエンドポイントと連携して正しく動作することを確認 | /process → /gpt/classify → /gpt/confirm の一連のフローが通ること |

### テスト実施方法
- Playwright MCPを使用した画面操作テスト（推奨）
- curl/httpie によるAPIリクエストテスト
- pytest + Flask test client によるユニットテスト

## チェックリスト（コードレビュー時）

レビュー者は以下のチェックリストを使用すること。

- [ ] 新しい変数名・関数名の導入: 全ての参照箇所で一貫して使用されているか
- [ ] 他モジュールの関数呼び出し: 関数定義のシグネチャと一致しているか
- [ ] セッションデータの読み書き: キー名が一致しているか、データソースが一貫しているか
- [ ] 環境変数の使用: ユーザー入力値と混同していないか
- [ ] 静的解析: flake8 でエラーが出ていないか
- [ ] テスト: 正常系・異常系・フロー通しのテストが実施されているか
